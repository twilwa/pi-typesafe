# Jev semantic lint pilot — pi-typesafe, 2026-09-21

Pilot of `@shahriarbijoy/eslint-plugin-jev@0.3.0` on this repository, the JS/TS pilot target for the
lint-convention lane (TES-93, child of TES-59). Implementation review:
[`package-review.md`](./package-review.md). Adoption across the fleet:
[`adoption-matrix.md`](./adoption-matrix.md).

**Model pinned: `jev-1.13.0`** — the id the API resolved for the `jev-latest` alias during the
benchmark below, now pinned in `eslint.semantic.config.js` so a moving alias cannot change results
silently.

## Budget

The lane allowed at most 40 live TypeSafe requests. **30 were used**, counted by instrumenting
`globalThis.fetch` in the ESLint process and its synckit worker rather than by estimating:

| Activity                                                 | Calls       |
| -------------------------------------------------------- | ----------- |
| Seed benchmark, 10 `name-matches-body` cases             | 10          |
| Pilot run over 5 source files (15 functions, cold cache) | 15          |
| Positive control on the known-bad fixture                | 1           |
| Observed-exception fixtures, 4 cases                     | 4           |
| **Total**                                                | **30 / 40** |

Every call returned HTTP 200. Re-running the pilot now costs **0 calls**: the on-disk cache is keyed
by `(backend, model, question, state)`, so only edited functions refetch.

## 1. Seed benchmark — `name-matches-body`, 9/10

`npm run bench:jev`, ten hand-labelled cases carried by the upstream repo, replayed at threshold
0.80 against `jev-1.13.0`. Total 4,766 input tokens, 1.27 s wall clock.

| case    | name            | note                    | expected | P        | result   |
| ------- | --------------- | ----------------------- | -------- | -------- | -------- |
| seed:1  | `getUser`       | get vs delete           | true     | 0.98     | PASS     |
| seed:2  | `validateEmail` | validate vs mutate+save | true     | 0.97     | PASS     |
| seed:3  | `fetchOrders`   | orders vs user          | true     | 0.97     | PASS     |
| seed:4  | `getUser`       | get with cache          | false    | 0.04     | PASS     |
| seed:5  | `saveOrder`     | validate then save      | false    | 0.09     | PASS     |
| seed:6  | `toJSON`        | protocol name           | false    | 0.30     | PASS     |
| seed:7  | `isEmpty`       | predicate               | false    | 0.03     | PASS     |
| seed:8  | `isEmpty`       | predicate that mutates  | true     | 0.96     | PASS     |
| seed:9  | `parseDate`     | parse with validation   | false    | 0.04     | PASS     |
| seed:10 | `logRequest`    | log vs metrics+forward  | true     | **0.79** | **FAIL** |

The single failure is a near-miss: `logRequest` increments a metric and forwards the request, and
the model put it at 0.79 against a 0.80 threshold. Separation is otherwise very wide — true cases
0.96–0.98, false cases 0.03–0.30 — so 0.80 sits in a genuine gap rather than in a cluster. **Keep
0.80.** Lowering to 0.75 would buy seed:10 and, on the evidence in §3, cost a false positive.

**Ten cases is a seed, not a calibration.** This is the only rule with labels at all.

## 2. Pilot run

```sh
set -a; . ~/.config/typesafe/env; set +a
npm run lint:semantic
```

Representative files, chosen to cover each architectural role named in `AGENTS.md` rather than to
maximise coverage:

| File              | Role                        | Units extracted | Units judged |
| ----------------- | --------------------------- | --------------- | ------------ |
| `src/sidecar.ts`  | failure/timeout handling    | 8               | 6            |
| `src/typesafe.ts` | SDK boundary                | 5               | 2            |
| `src/config.ts`   | config parsing, throw-heavy | 4               | 4            |
| `src/verdict.ts`  | runtime response checks     | 1               | 1            |
| `src/checks.ts`   | question policy             | 1               | 1            |
| **Total**         |                             | **19**          | **15**       |

`src/context.ts` (13 units) and `src/audit.ts`, `src/extension.ts` were left out to stay inside
budget; they are unjudged, not clean.

The four extracted-but-unjudged units (`pull`, `cancel`, `systemOne`, `reset`) are object-literal
properties, which `name-matches-body` excludes by design — the consuming interface picks those
names, not the body's author — and they carry neither a leading comment nor a `throw`. 15 units
selected, 15 requests: **one request per function, and no unit was silently skipped.**

### Findings: none

| Rule                    | Units/sites judged | Flagged | Assessment                          |
| ----------------------- | ------------------ | ------- | ----------------------------------- |
| `name-matches-body`     | 15 units           | 0       | calibrated (§1); result trustworthy |
| `comment-matches-code`  | 4 units            | 0       | **uncalibrated**                    |
| `helpful-error-message` | 13 throw sites     | 0       | **uncalibrated**                    |

Only 4 units carry a leading comment that is not a pragma (`configuredBaseURL`, `readConfig`,
`createTypeSafe`, `verdicts`), so `comment-matches-code` had very little to judge here.

A zero-finding run is the outcome most easily mistaken for a working check, so it was verified
rather than assumed — see §4.

### Latency

Per-request 67–234 ms, median ~120 ms. Whole 5-file run: **3.3 s wall clock** cold, at
`concurrency: 4`. Warm, the run is offline and adds no measurable time. The configured per-file
deadline is 30 s, roughly ten times the observed cost of the largest file, so deadline skips — which
the plugin would _not_ report (see `package-review.md` §7) — were not in play.

## 3. Observed exceptions

Zero findings means zero _observed_ false positives, which is too weak a basis for tuning. The four
functions in this repo most likely to be misread were therefore extracted into
`test/fixtures/jev-lint/observed-exceptions.jsonl` and measured directly, to record how much margin
the 0.80 threshold actually has:

| case  | name           | why it is a risk                                                | P        | margin to 0.80 |
| ----- | -------------- | --------------------------------------------------------------- | -------- | -------------- |
| obs:1 | `record`       | reads as the imperative verb "record"; body is a type predicate | **0.53** | 0.27           |
| obs:2 | `inRange`      | adjective phrase, no verb at all                                | 0.04     | 0.76           |
| obs:3 | `hazard`       | noun-named factory returning a question                         | 0.16     | 0.64           |
| obs:4 | `questionsFor` | also filters by enabled-ness, which the name omits              | 0.08     | 0.72           |

`record` at 0.53 is the honest limit of this configuration: **noun/verb ambiguity is this
repository's false-positive risk**, and a threshold below ~0.55 would start flagging it. Re-run with
`node scripts/jev-bench.ts test/fixtures/jev-lint/observed-exceptions.jsonl` before any threshold
change.

No per-repo custom `jev/check` questions are proposed for pi-typesafe — see the matrix for the
reasoning and for the repos where they are proposed.

## 4. Is the check actually working?

A clean report from a semantic linter is worth nothing unless a dirty one would have looked
different. Three controls, all reproducible:

1. **Positive control (1 call).** The same rules, thresholds and model against
   `test/fixtures/jev-lint/sample.ts`, a fixture with a lying name, a contradicting comment and the
   message `"Error 42"`. All three rules fire:

   ```
   5:1   warning  Comment on "getUser" contradicts what the code does (P=0.91, threshold 0.80)
   6:23  warning  Name "getUser" does not match what the body does (P=0.94, threshold 0.80)
   7:28  warning  Error message "Error 42" gives the reader nothing to act on (P=0.95, threshold 0.85)
   ```

2. **Call count.** 15 requests for 15 selected units, all HTTP 200. The judging demonstrably ran.

3. **Missing-key control.** `test/unit/jev-lint.test.ts` asserts that with no key reachable the run
   reports its rules _inactive_ rather than clean, in machine-readable output.

## 5. Judgement: useful?

**Worth keeping as an advisory check; not worth gating anything on.**

- `name-matches-body` is the one rule with evidence behind it: 9/10 on the seed set, wide
  separation, and 0.27 of margin on this repo's nastiest true negative. Cheap, fast and cached.
- The zero findings are a fair result for an 8-file repository that has already been through two
  rounds of review — not evidence that the rules do not work, given §4, and not evidence that the
  unjudged 40% of the codebase is clean either.
- The cost is negligible: 30 calls, ~11k input tokens, well under a cent at $0.042/M input.
- The real limitation is structural, not statistical. The API sees one function at a time —
  name, signature, comment, body — so it cannot speak to whether `sidecar.ts` and `verdict.ts` agree
  about a contract, which is where this repository's actual risk lives. Deterministic lint,
  typecheck and tests stay authoritative.

### Recommended follow-ups

1. Keep all three rules advisory at `warn`, out of `npm run check`. Do not promote to `error`.
2. Leave `comment-matches-code` and `helpful-error-message` labelled **uncalibrated** in the README
   until a labelled set exists. Upstream reports precision 0.37 for `comment-matches-code` on its
   own bench; this pilot cannot confirm or refute that with 4 units and 0 findings.
3. `helpful-error-message` at 0.85 flagged none of 13 terse internal messages
   (`"Malformed response"`, `"Invalid choice"`, `"Unknown check"`). Whether that is correct is a
   judgement call this pilot cannot settle: the threshold may be too high for this style, or the
   messages may be fine in context. Label a set before touching 0.85.
4. Extend to `src/context.ts` and the remaining files on the next run — it costs ~19 more calls
   cold, and the cache makes it free thereafter.
